title: Why agreeing is hard

You have built a container runtime, so somewhere in your system there is state that other programs depend on: which containers exist, their IDs, their resource limits. Today that state probably sits in one place. If that machine reboots, every program that consults the state stalls until it comes back, and if it dies, everything depending on it breaks. The obvious move is to store the state on three servers instead of one, so the loss of any single machine costs you a copy, not the service.

Then the next request arrives, `create container "web-1"`, and a humble question turns vicious. The three servers each heard about the request through a network that can lose, delay, or reorder messages. Which server actually decides? What happens when the network makes two servers disagree about whether the deciding server is even alive? This chapter is the story of why "just copy the data" does not end the problem but starts it.

:::: crux
Why can't a cluster of servers that each saw the same requests just agree on what happened, and what is the least we must assume so that they can agree at all?
::::

## Copying the data inherits the agreement problem

[Replication]{.term key="replication" def="Keeping identical copies of some state on several machines so that the loss of one machine does not lose the state."} sounds like a backup plan, and it does solve the narrow problem it advertises: if one disk or one machine dies, the data still exists elsewhere. Replication is what you reach for when you want service with no downtime even if a machine fails, and it handles the clean case well, the failure of a single replica that simply stops [@F8]. The trouble is that your registry is not a pile of bytes. It is a live map that changes as containers are created and deleted, and now every change has to land on every copy.

The moment there is more than one copy and more than one client, copying becomes an agreement problem, and the agreement that is needed is a single order of operations, stronger than agreeing on each value separately. Two clients create and delete the same container name at nearly the same time, and the three servers must end with the same final map, which means they must all apply the two operations in the same order.

The standard way to think about this is the [replicated state machine]{.term def="A design where identical deterministic state machines on several servers process the same commands in the same order, so they compute identical copies of the same state."}. State machines on a collection of servers compute identical copies of the same state and keep operating even when some of the servers are down [@F1]. Real systems use this shape constantly, often without naming it: large-scale systems with a single cluster [leader]{.term def="The one server in a cluster that is currently in charge of deciding the order of operations."}, such as the Google File System (GFS), the Hadoop Distributed File System (HDFS), and RAMCloud, keep a separate replicated state machine to manage leader election and store configuration that must survive leader crashes, and Chubby and ZooKeeper are examples of that shape [@F2]. The idea leans on a property your registry already has. A map from container name to config, driven by `create` and `delete` commands, is deterministic: apply the same commands in the same order and every server ends with the identical map, with no coordination needed at apply time.

So the hard part shrinks to one question: how do the servers agree on the order? On each server, a [consensus]{.term def="The problem of getting a set of servers to agree on a single value, or a single sequence of values, despite failures and an unreliable network."} module receives commands from clients and adds them to its log, and it communicates with the modules on the other servers so that every log eventually contains the same requests in the same order, even if some servers fail [@F3]. Consensus on a log of commands is a clever substitution. Agreeing on every value separately means negotiating each `create` and each `delete` as its own three-way argument. Agreeing once on the contents and order of a log means the servers only ever argue about one thing, and the log then orders the commands for the replicas, which is precisely why a service keeps a log alongside its state machine state: the log is the instrument that lets replicas agree on a single execution order [@F9].

What does "agree" have to guarantee, precisely? Lamport's statement of the requirements is the cleanest: only a value that was proposed may be chosen, only a single value is chosen, and a process never learns that a value has been chosen unless it actually has been [@F5]. Notice what is missing from that list. Nothing says the answer must arrive quickly. That split, between what must always hold and what usually holds, will come back to shape everything Raft does.

:::: {.misconception title="Replication is a backup problem"}
Copying data to more servers does protect against one disk or one machine dying. What the backup framing misses is that the copies are live and concurrent, so the hard part was never storing the data. It is deciding what happened, in what order, when the network delivers imperfect reports of the same events. A backup is a copy made after the fact. A replica is a participant in every decision.
::::

## The world we agree in: the fault model

Before we can say whether an agreement protocol is correct, we have to fix what it is standing on, and that means being honest about how bad the network and the machines are allowed to get. This contract is called the [fault model]{.term def="The explicit list of failures a protocol is designed to tolerate, and the failures it assumes never happen."}, and every later chapter in this topic runs inside it.

The network side is worse than a first guess. Raft must maintain safety under all non-Byzantine conditions, which includes network delays, [partitions]{.term key="partition" def="A network failure that splits the servers into groups that can talk within the group but not across groups."}, and packet loss, duplication, and reordering [@F10]. The formal specification says it bluntly: the network may reorder, drop, and duplicate messages [@F11]. A partition deserves special attention, because it is the failure that produces this chapter's disaster: the network silently splits, each group looks healthy from inside, and no message between groups gets through at all.

The server side has a specific shape. Servers are assumed to fail by stopping, and they may later recover from state on stable storage and rejoin the cluster [@F12]. This is the [crash-recovery]{.term def="A fault model where servers fail by stopping and may later restart, reloading their saved state and rejoining the system."} model, and it draws a hard line against [Byzantine]{.term def="A fault model where failed servers may behave arbitrarily, including sending false or contradictory information."} faults: Raft handles fail-stop but not Byzantine failures, so servers are assumed not to lie or collude [@F13]. Every message a server sends is something it genuinely believes. That assumption is doing enormous work, and this topic keeps faith with it throughout: nobody lies, machines just stop, lose their volatile memory, and come back.

Coming back is a designed-for event, not an afterthought. Raft retries its requests to a crashed server indefinitely, so when the server restarts, the pending request completes and it rejoins [@F16]. To make that safe, each server must persist enough information to stable storage to survive a restart [@F17], and production libraries enforce this at the API level: the etcd raft library requires that no messages be sent until the latest hard state has been persisted to disk, along with all entries from earlier batches [@F18]. Reboot and rejoin is a normal Tuesday.

There is one more thing Raft refuses to assume, and it surprises people: time. Raft does not depend on timing to keep the logs consistent, and faulty clocks and extreme message delays can, at worst, cause availability problems, not incorrect results [@F14]. Safety holds even in an asynchronous model where messages and processors proceed at arbitrary speeds [@F27]. Hold onto that one. By the end of this chapter you will know exactly why the designers drew that line so firmly.

## Split brain: one cluster, two truths

The natural design for three servers holding one registry is one leader plus [followers]{.term def="The servers in a cluster that accept the leader's decisions and replicate its state."}, so let us walk that design into its failure. The leader sends periodic [heartbeats]{.term def="Small periodic messages a leader sends to followers to signal that it is still alive and in charge."} to the followers, and a follower that stops hearing heartbeats within its timeout concludes the leader is gone and promotes itself. This failover is exactly what you would write on the first try, and it is exactly what our lab does.

Here is the trap underneath it. A machine cannot distinguish a crashed server from a broken network, because the symptom is identical in both cases: no response to a query over the network [@F20]. The dissertation states the general form: in all practical settings it is impossible to distinguish a failed server from a slow server, and this is the key characteristic of an asynchronous system [@F21]. A timeout proves only that *you* stopped hearing from the peer. The peer may be dead, paused, or partitioned away from you while still talking to everyone else.

Now run the failure. The leader pauses, or a partition drops its heartbeats in one direction. A follower's timeout fires, and the follower declares itself the new leader. The lecture notes walk this exact scenario: if the backup decides the primary is down and takes over as coordinator while the primary is still running, a network partition produces [split brain]{.term def="A failure state in which two servers in one cluster simultaneously believe they are the leader."}, two servers each acting as coordinator [@F24]. The old leader never died. It is still alive and still serving clients, and each of the two leaders now accepts writes the other never sees. Worse, since failure detectors can mistakenly report a live-but-slow leader as failed, a failover system must not just pick a new leader, it must neutralize the suspected old one: once a server has seen a larger term number, it no longer accepts requests from a leader with a smaller number [@F22; @F25]. Our naive design has no terms, no votes, and no way to neutralize anything.

## Why the wall clock can't referee

There is a tempting fix, and it is worth taking seriously before dismissing it, because seeing exactly why it fails teaches you what the real fix must contain. Give the old leader a time limit. When B promotes itself, it stamps its leadership with the current time, and any request from a leader whose timestamp is older than the limit gets rejected. This is [fencing]{.term def="Invalidating a stale leader's actions by attaching a number or timestamp to every decision and rejecting decisions that carry a stale one."}, and the number being compared is a fencing token.

The timestamp version fails on both halves of its own machinery. First, comparing timestamps across machines requires trusting the clocks of those machines, and a lease-based fence assumes a bound on how far two machines' clocks can drift apart over a period [@F26]. That bound is an operational hope, not a property of hardware. Second, even a correct clock does not help, because a process can pause. Discovering and maintaining the clock-drift bound is operationally hard precisely because of scheduling and garbage collection pauses, virtual machine migrations, and clock rate adjustments for time synchronization, and if those assumptions are violated the system can return arbitrarily stale information [@F23]. Picture the old leader in the lab mid-GC-pause, holding a lease it believes is valid, waking to serve `delete("web-1")` with its timestamp while B is already serving `create("web-1")` with a newer one. The lease says yes. The world has moved on.

Notice that both failure paths are the timeout misconception again, wearing a clock. A lease tells you what your own clock believed about your own liveness. It cannot tell you what the rest of the cluster has decided in the meantime, and no single machine's clock is authority over a distributed decision. This is exactly why Raft refuses to put correctness in the hands of time: safety must not depend on timing, and faulty clocks can cost at most availability, never correctness [@F14]. The production evidence agrees. The etcd raft library's core does not depend on clocks, and its optional lease-based read optimization is the one part that does rely on the clocks of all the machines in the group, which is why that optimization is an opt-in speedup rather than the foundation [@F15].

So what does Raft use instead of clocks to demote a stale leader? Numbers that the cluster counts, not time that a machine measures. Raft invalidates a stale leader with term numbers: a candidate or leader that learns its term is out of date immediately reverts to follower, and a server rejects any request carrying a stale term number [@F28]. In the etcd raft library, a message arriving with a higher term makes its receiver become a follower at that higher term, which is how a stale leader is forced to step down [@F29]. How those terms get chosen and voted on is chapter 3's subject. What this chapter needs is the shape of the answer: authority comes from something the servers count together, not from something any one of them reads off its own clock.

## No perfect answer exists, so pick your sacrifice carefully

At this point you might reasonably ask whether the whole thing is just badly engineered so far, and whether some cleverer protocol could make split brain impossible while still tolerating crashes and a messy network. The honest answer is no, and the reason is one of the famous results of the field. In 1985, Fischer, Lynch, and Paterson proved what is now called the [FLP impossibility result]{.term def="The 1985 proof that in a fully asynchronous system, no deterministic consensus protocol can guarantee that it terminates if even one server may crash."}: in a fully asynchronous model, consensus cannot be solved even if just a single server stops, and the result was published in the Journal of the Association for Computing Machinery in April 1985 [@F30; @F31]. Put as a protocol constraint, no fault-tolerant consensus protocol can deterministically terminate in a purely asynchronous model [@F32].

It is worth being precise about what this does and does not say. It does not say consensus is hopeless, and it does not say your cluster will stall forever. It says that if you demand a protocol that is guaranteed to finish in bounded time under every possible interleaving of delays and crashes, including adversarial ones, then no deterministic protocol can give it to you. Something has to give. Every usable consensus algorithm is a choice about what to give up.

Raft's choice splits the promises in two, and this split is the most important idea in the chapter. Its safety never depends on timing: the system must not produce incorrect results just because some event happens more quickly or slowly than expected [@F33]. Two leaders serving conflicting writes is a safety violation, and Raft rules that out structurally, by the counting we will meet in the next section, not by hoping the timing works out. But availability, the ability to respond to clients in a timely manner, inevitably does depend on timing [@F33]. Raft accepts that it can occasionally stall, for example when elections collide, and buys back liveness in practice with a relaxed model of time. This idea goes by the name [partial synchrony]{.term def="A system model that assumes timing is not fully arbitrary, only that message delays and processing times eventually stay within some loose bound."}: rather than assume the fully asynchronous world where anything can take any amount of time, Raft assumes the real world, which is usually well behaved for long stretches.

Concretely, Raft requires broadcast time to be much less than the election timeout, which in turn must be much less than the [mean time between failures]{.term key="mean time between failures" def="The average time a machine or system runs before its next failure."} [@F34]. Each link in the chain does a specific job. Keeping broadcast time an order of magnitude below the election timeout means heartbeats reliably arrive before followers time out, and it also makes split votes unlikely. Keeping the election timeout a few orders of magnitude below the mean time between failures means the system makes steady progress rather than spending its life re-electing leaders [@F35]. When the world cooperates, and in practice it usually does, Raft finishes. When it does not, Raft is merely slow, never wrong. And because FLP rules out a deterministic guarantee, chapter 3's elections use randomized timeouts to break ties, which is exactly the kind of sacrifice the result forces.

## Majorities: the counting trick

We are left with the real question. If the network can partition, if timeouts cannot be trusted, and if clocks are out, what mechanism can possibly let a cluster make a decision that survives the failure of the decider? The answer is arithmetic, and you can verify it yourself.

Raft requires that a decision be confirmed by a [majority]{.term def="More than half of the servers in a cluster."} of the servers, a [quorum]{.term def="The minimum number of servers that must agree for a cluster decision to count."}: an entry counts as committed only once the leader that created it has replicated it on a majority of the servers [@F36]. The magic is in what any two majorities share. Count it for three servers. A majority is at least two, and any two groups of two out of three must overlap, since two plus two is four but there are only three servers. In general, in a cluster of $n$ servers a majority is $\lfloor n/2 \rfloor + 1$ [@F38], and any two majorities therefore share at least one server. This is [quorum intersection]{.term def="The property that any two majorities of a cluster must share at least one common server."}, and the shared server is the witness that carries information forward.

Here is how that witness earns its pay, as a preview of chapter 4. Suppose an old leader replicated an entry on a majority, and then died. A new leader cannot be elected without collecting votes from a majority. The old leader's majority and the new leader's majority overlap, so at least one server both accepted the entry from the old leader and voted for the new one [@F37]. Whatever that server knows, the new leader can be made to learn, which is how a committed entry survives later elections instead of being quietly forgotten. Split brain dies here: two conflicting decisions would each need a majority, and two majorities cannot be disjoint, so the two truths from the lab cannot both be confirmed.

The arithmetic also tells you how many machines to buy, and this is the operator-facing version of the same counting. For a cluster with $n$ members the quorum is $\lfloor n/2 \rfloor + 1$, which gives the failure-tolerance table etcd publishes: a 3-member cluster tolerates 1 failure, a 5-member cluster tolerates 2, and a 7-member cluster tolerates 3 [@F39]. The table has a quiet lesson in it. Compare a 4-member cluster, which needs a quorum of 3 and tolerates 1 failure, with a 3-member cluster, which needs a quorum of 2 and also tolerates 1. The fourth machine bought you nothing but a bigger quorum. That is why etcd recommends an odd number of members: an odd-size cluster tolerates the same number of failures as the next even size but with fewer nodes [@F40]. There is no hard limit on cluster size, but an etcd cluster probably should have no more than seven nodes [@F41], so three, five, or seven is the practical menu.

B's election timeout is 150 ms and C's is 250 ms, so B's timer runs out first and B promotes itself. B's heartbeats still reach C and keep resetting C's timer, so C never promotes itself. Neither B nor C can tell whether A crashed or is merely cut off, which is the failed-versus-slow problem in miniature.
2. Split the cluster into two groups, A plus C and B alone, dropping every message between the groups. B times out and broadcasts its announcement, but the broadcast can only reach servers in B's group, which is nobody. A and C never hear it, A keeps leading C, and each side confirms its own leader. Broadcasting does not help when the partition blocks the broadcast itself.
3. A quorum of 9 is 5, and only 5 servers remain, so a majority still exists and the write can commit, on exactly 5 servers. Had one more server failed, no majority would exist, the write could not be confirmed, and the cluster would refuse until servers recovered. That refusal is an availability failure. The safety property, never returning an incorrect result, is the one Raft's design never sacrifices, because safety rests on quorum intersection rather than on timing.
4. Raft gave up guaranteed termination, which is a liveness property, and kept safety unconditionally, so unlucky timing can make it stall but never make it wrong. It assumed partial synchrony, expressed as the timing requirement that broadcast time be much less than the election timeout, which in turn is much less than the mean time between failures, so elections settle and progress resumes in practice.
